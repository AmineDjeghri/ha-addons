# 3. Conventions

The rules every change follows.

## Code

- Use the `make` targets (`make help`): CI runs the same ones.
- Docstrings on public functions and classes (Google style): they generate the API reference.
- Settings come from `backend_settings.py` / `frontend_settings.py` (pydantic-settings, `.env`),
  never `os.environ` scattered in the code. Secrets are `SecretStr`.
- Logging with the package's loguru logger, not `print`:

    ```python
    from personal_app_backend.backend_settings import logger

    logger.info("Loaded {} items", count)
    ```

- Log, then raise; do not swallow exceptions:

    ```python
    if not path.exists():
        logger.error(f"File not found: {path}. Current directory: {Path.cwd()}")
        raise FileNotFoundError(path)
    ```

    In an `except` block, `logger.exception(...)` logs the message and the stack trace. Not
    raising is fine only when a loop must go on after one failure.

## Branches and pull requests

1. Branch off `main`: `feature/<name>` or `bugfix/<name>`.
2. Run `make check` ([4. Testing](4.testing.md)), then open a pull request to `main`. Its **title**
   follows the commit convention below: it becomes the squash commit and decides the version.
3. Pull requests are squash-merged. Pushes to `main` that touch this add-on are released by CI.

Never edit a version in `pyproject.toml` or `config.yaml`, or create a tag by hand:
semantic-release does it.

## Commit convention

`[emoji] <type>[(<scope>)][!]: <description>`, the emoji is optional ([Gitmoji](https://gitmoji.dev/)).

| Emoji                | Type                                                        | Aliases                   | Release |
|----------------------|-------------------------------------------------------------|---------------------------|---------|
| 🐛                   | `fix`                                                       | `bugfix`, `hotfix`        | patch   |
| ⚡️                   | `perf`                                                      |                           | patch   |
| ✨                   | `feat`                                                      | `feature`                 | minor   |
| 💥                   | `feat!`                                                     | `BREAKING CHANGE:` footer | major   |
| ♻️ 📝 🎨 🧪 🔧 👷 📦 | `refactor`, `docs`, `style`, `test`, `chore`, `ci`, `build` |                           | none    |

A `!` or a `BREAKING CHANGE:` footer makes any allowed type a breaking change (major release).

```text
✨ feat(metrics): add disk usage
🐛 fix(backend): handle a missing sensor
💥 feat!(api): remove the v1 endpoint
```

Scopes are optional. Common scopes: `backend`, `frontend`, `addon`, `ci`, `deps`. The commit message is
checked on commit (commitizen) and the pull request title by `ci.yml`.

The repository holds other add-ons, and semantic-release reads every commit since the last
`personal-app-v*` tag. Keep commits that touch several add-ons separate, or a change to another add-on
can bump this one.

## Secrets

- Never write a credential to a file of the repository, even untracked: use environment variables or `.env` (git-ignored).
- `detect-secrets` runs on commit. For a line that intentionally references a secret placeholder
  (`${{ secrets.X }}`), add `# pragma: allowlist secret`. File-level exclusions in
  `.pre-commit-config.yaml` only for recurring false positives; never exclude a whole workflow to
  silence one line.

## Environment variables

Adding, renaming or removing one, in the same change: the setting in `backend_settings.py` or
`frontend_settings.py`, `.env.example`, `config.yaml` and `run.sh` when it is an add-on option, and
the workflow `env:` if CI needs it.

## Dependencies (Renovate)

Renovate (`.github/renovate.json5`) opens pull requests with the `renovate` and `dependencies` labels
for the whole repository. Review every one; a dependency dashboard issue lists the pending ones.
`uv.lock` makes builds reproducible, and the add-on image installs from it.
