# Beets addon (addons/beets/ in ha-addons)

From-scratch CLI-tool addon built Aug 2026 (PR #17). Beets 2.13.1 auto-tagger for the Navidrome + Octo-Fiesta music stack. `config.yaml` version mirrors the upstream beets version so HA surfaces updates.

## Architecture
- `build.json` → `ghcr.io/home-assistant/{arch}-base:latest` (personal-app pattern, amd64/aarch64/armv7), `init: false`
- `Dockerfile`: `apk add bash curl jq ca-certificates chromaprint ffmpeg inotify-tools build-base(→--virtual .beets-build)` → `uv tool install --python 3.14 --default-index https://pypi.org/simple --index-strategy unsafe-best-match "beets[fetchart,lastgenre,embedart,titlecase,chroma]==${BEETS_VERSION}"` (CLI flags REQUIRED — see SKILL.md: base image /etc/pip.conf wins over env vars; PR #18 env-var fix failed, PR #19 CLI flags built) → `apk del .beets-build` → `ln -s /root/.local/bin/beet /usr/local/bin/beet` → `COPY run.sh` + chmod + `ENTRYPOINT ["/run.sh"]`
  - `ENV BEETS_VERSION=2.13.1` = single source of truth; the bump job sed-replaces it
  - Alpine `chromaprint` package provides the `fpcalc` binary (chroma plugin) — no manual wget
  - uv fetches a managed CPython (musl) — no system python needed
- `run.sh`: reads bashio options ONCE at startup → writes `/data/beets/config.yaml` → startup full incremental import → main loop: daily sweep (HH:MM) + duplicates check + `inotifywait` debounce (default 300s) → imports parent dirs of new audio files
- All beets runs flock-serialized on `/data/beets/import.lock` (`flock -n` → skip if busy)
- Persistence: `/data/beets` (library.db, config, import.log, lock) — included in HA full backups (supervisor per-addon data stage)
- **Manual scan = restart the addon** (startup import). A `.beets-scan` trigger-file mechanism was proposed and REJECTED by the user — don't re-add
- Duplicates job is **report-only**: `beet duplicates -k title -k albumartist` (user explicitly wants flagging, never `--delete`)

## Addon options (config.yaml) — defaults matter
- `quiet_fallback: asis` — Octo-Fiesta downloads rarely match MusicBrainz; asis imports them with filename tags instead of skipping. `fetchart.fetch_for_asis: yes` pairs with it (else no online art for asis imports)
- `duplicate_action: skip` — safe headless default; `remove` on re-import of a known album deletes the SAME files (self-duplicate)
- `incremental: true`, `timid: false` — exposed as options; timid only matters with `quiet: no` which HANGS headless (beets prompts on stdin). `resume` fixed to `skip` for the same reason
- `acoustid_apikey` (optional) — chroma fingerprint lookups need a free key; without it chroma does nothing
- `navidrome_url/user/password` (optional) — Subsonic `startScan` after imports. URL e.g. `homeassistant.local:4533` (same as octo-fiesta `subsonic_url`). Token auth: `t=md5(password+salt)`, `s=salt`, `v=1.16.1`, `c=beets-addon`, `f=json`. Caveat: Navidrome "Enable password authentication" must be on. Empty values → rescan skipped silently (no error)
- watch debounce 300s default (batch → more complete albums)

## Headless beets constraints
- `quiet: yes` required (no TTY); `quiet_fallback` decides weak matches: `skip` | `asis`
- `incremental: no` = full re-scan on every sweep; caveat: re-import `asis` can overwrite better existing tags with filename-derived ones — prefer targeted `beet modify` for fixes (misnamed-songs cleanup toolkit: `chromasearch`, `modify +=/-=`, `duplicates`)

## beets domain knowledge (2.13.x)
- `create_backup_before_migrations` (2.13.0, default yes): auto `.bak` of library.db before schema migrations; naming `<db>-before-<table>-<migration>.bak`, one per migration ever run, kept forever, a few MB each (index DB only)
- Multi-genre `genres` field (2.7+): list, written as separate GENRE tags; Navidrome reads them
- **Per-song genres — `lastgenre.source` (user-corrected Aug 2026):** beets CAN apply per-track genres. Default `source: album` = one genre set per album applied to all tracks; `source: artist` = per artist; `source: track` = per-song genres (fetches track-level Last.fm tags — more API calls, sparser coverage). Author-confirmed (beets-users thread, Adrian Sampson: "The lastgenre plugin can be configured to fetch separate per-track genres"). **LESSON: beets has a config knob for almost everything — check the plugin reference BEFORE claiming a feature doesn't exist** (I asserted per-song genres weren't a thing; the user said "search the web" and the docs proved me wrong). Re-genre existing library per-song: `beet lastgenre -A` (albums: `beet lastgenre`); `lastgenre.force: yes` overwrites existing values.
- `has_cover_art` query (2.9), `chromasearch` (2.9 — fingerprint search), `modify +=/-=` (2.13), `duplicate_action: upgrade` (unreleased), `editor` config (unreleased)
- `fetchart.fetch_for_asis` (2.13): online art for asis imports; never replaces existing art unless `force`
- Python 3.14 supported since 2.9.0; project moved to uv/hatchling (2026)

## Post-deployment operational notes (live HA run, PR #20)
- **First start on a fresh `/data` DB = FULL import, not incremental** — `--incremental` skips albums already in the DB; an empty DB means EVERYTHING is new. With per-album MusicBrainz lookups (rate-limited ~1 req/s) a large library takes HOURS. Don't diagnose "stuck" until `import.log` or the Log tab shows no progress for a long time.
- **Beets' own output is NOT in the addon Log tab by default** — run.sh redirects it to `/data/beets/import.log`; the Log tab only shows the run.sh INFO/ERROR lines ("Importing:", "Import finished OK"). First-run "only two lines then silence" is normal. PR #20/#21 stream beets output to BOTH: `beet ... -v import ... 2>&1 | tee -a "${LOG_FILE}"` inside the flock subshell with `set -o pipefail` (keeps the real exit code through the pipe). **Verbosity = `-v` (PR #21), NOT `-vv`** — the user asked for `-vv` twice, saw the result in the Log tab, and rejected it as unreadable ("not many lines of ids… I just wanted simple logs with song names, albums, genres, what changed"). `-vv` floods the log with DEBUG noise: `Sending event: …` hook lines, per-event `database_change`, and chroma's `matched recordings [<uuid>, …]` MusicBrainz-ID lists. `-v` keeps per-album INFO lines only: `Looking up/Tagging <artist> - <album>`, `Evaluating N candidates`, `Matched: …`, `Importing as-is.`, `0 of N items replaced`, `fetchart: using local image …`, `lastgenre: Resolved: […]`.
- **`Sending event:` lines LEAK even at `-v` (PR #23) — root-logger debug:** `beets.plugins.send()` logs `log.debug("Sending event: {}", event)` on the ROOT `beets` logger, and the threaded importer's thread-local logging leaves the root more permissive than plugin loggers (plugin loggers ARE gated during import stages — `_set_log_level_and_params` → `max(DEBUG, WARNING - 10*verbosity)` → INFO at `-v` — which is why the chroma UUID lists disappear at `-v` while root-level event traces stay). Diagnostic signature: **IDs gone, events remain** = the running build IS `-v`; the leak is beets internals, not a stale image. Deterministic fix = filter the pipe (no beets knob): `beet -c "${CONFIG_FILE}" -v import "${args[@]}" 2>&1 | awk '!/^Sending event:/' | tee -a "${LOG_FILE}"` inside the flock subshell. Use `awk`, NOT `grep -v`: grep exits 1 when nothing passes through (an incremental sweep with zero output) → `pipefail` flags a SUCCESSFUL import as 'ERROR: import failed'.
- **`import.log` auto-rotation (PR #20):** it lives in `/data` → inside HA full backups → unbounded growth bloats archives. At startup: `if [ -f "${LOG_FILE}" ] && [ "$(stat -c %s "${LOG_FILE}" 2>/dev/null)" -gt 10485760 ]; then mv -f "${LOG_FILE}" "${LOG_FILE}.1"; fi` → bounded ~20 MB. The Log tab itself is supervisor/journald-bounded (self-rotating) — no disk risk there, just noise.
- **`beet version | head -1` is WRONG on first run** — the migration backup message ("Created database backup at: '...-before-items-multi_genre_field.bak'.") prints BEFORE the version line, so the startup banner showed the backup path instead of `beets 2.13.1`. Fix: `beet version | grep '^beets ' | head -1`.
- **`create_backup_before_migrations` visible in the wild:** the `.bak` in the startup log = beets 2.13.0 migration backup ran (here: `multi_genre_field`, the 2.7.0 multi-genre feature) — proof of the built-in feature, not a bug.
- **Live HA verification via MCP:** `ha_get_addon(slug=..., include_stats=true)` shows state/version/options; `ha_get_logs(source="supervisor", slug=...)` returns the addon container log. Both worked from the agent to confirm "started + importing" without touching the user's HA UI.
- **Progress UX note:** `-v` + tee gives ~9 readable lines per album — album/artist, match result, replaced count, genre, art. That IS the user's preference; never propose `-vv` for "more detail" again (tried twice, rejected both times as noise).
- **Merged main ≠ running addon (manual-reinstall consequence):** the container keeps running the image built at install time until the uninstall→install cycle. If the user reports OLD behavior after merges (e.g. "I still see `Sending event:` spam" while `-v` is in main), the running image is simply stale — check `gh pr view <n> --json state` + `git fetch && git log origin/main` first, then tell them to do the manual reinstall (with the docker cp DB backup) rather than touching code.

- **"Evaluating 0 candidates" for famous albums during the bulk first import = MusicBrainz rate-limiting** (~1 req/s per IP; the mass import hammers it) — transient, not a config error; those albums match on later incremental runs. At `-vv`, chroma's `matched recordings [<uuid>, …]` lines are the AcoustID fingerprint candidates across releases — normal, that's how fingerprint matching works.
- **`titlecase: <field>: does not exist on <class …>` lines = benign noise (appears in the PR #25 `-vv` build):** the titlecase plugin applies `fields: [title, album]` to BOTH object types during candidate matching — `AlbumInfo` has no `title`, `TrackInfo` has no `album` → it logs "does not exist" and skips; real titlecasing still works (`title: Let Me Love You (Zedd remix) -> (Zedd Remix)`). Fix: add `!/^titlecase: .*does not exist/` to the awk blacklist (SHIPPED in PR #28). Don't tell the user it's a config error — the red lines alarmed him once.
- **"What did beets modify?" — log greps (run in Terminal & SSH, NOT from Hermes — no docker exec access; import.log rotates to import.log.1 at 10 MB → grep both):**
  - genre changes with song names: `grep -B6 -A8 '^    [+-] ' /data/beets/import.log` (`- Dance` = removed, `+ House` = added; the `lastgenre: <artist> - <album> - <track>` line above the block names the track)
  - title rewrites: `grep 'titlecase: title: .*->' /data/beets/import.log`
  - albums actually re-tagged: `grep -E '[1-9][0-9]* of [0-9]+ items replaced' /data/beets/import.log`

## Matching semantics — verified from beets source + live logs (PR #24 era)
- **quiet mode auto-applies ONLY strong matches** (`distance < strong_rec_thresh`, 0.05 here); medium (`< medium_rec_thresh`, 0.3) is NOT auto-applied headless → falls to quiet_fallback (asis). The ONLY knob that widens auto-apply is strong_rec_thresh.
- **chroma ID match = strong regardless of distance:** when AcoustID resolves the fingerprint to an exact release ("Searching for discovered album ID: <uuid>" → "ID match."), beets treats it as a strong match → auto-applied even at 0.05 with `Success. Distance: 0.00` + `Match (100.0%)`. That's why fingerprint-resolvable albums (ABBA, Adele) get fully tagged while search-fallback albums (A$AP Rocky, Alok) fall to asis at 0.25–0.70 distances.
- **"0 of N items replaced" after a 100% match = GOOD:** the files were already tagged identically (Tidal metadata == MB) — beets links the MB IDs in the DB and changes nothing visible. Not a failure.
- **"Missing tracks (15/19 - 78.9%)" = partial-album folders:** this user's library holds SELECTED tracks per album folder (4 of ABBA Gold's 19). Normal; beets imports what's there — but it's exactly why default weights (below) inflated search distances.
- **Distance weights — user's custom set ported verbatim (PR #24, feat/beets-distance-weights):** current beets DEFAULTS penalize exactly what Tidal rips trip on — verified from `beets/config_default.yaml`: `data_source: 2.0`, `missing_tracks: 0.9`, `unmatched_tracks: 0.6`, `media: 1.0`, `country: 0.5`, `album_id/track_id: 5.0`, `track_title: 3.0`, `track_artist: 2.0`, `track_index: 1.0`. His config (zeros on edition-level mismatches, stricter on track details): `data_source: 0.0, missing_tracks: 0.0, explicit: 0.0, country: 0.0, media: 0.0, tracks: 2.5, track_title: 4.0, track_index: 4.0, track_length: 2.0, track_artist: 5.0, unmatched_tracks: 0.0`. Rationale: streaming rips with bonus/partial tracks and digital-media source shouldn't be pushed to asis; unknown weight keys (e.g. `explicit`) are ignored harmlessly. **Audit lesson: "is it the same as my config?" must be checked key-by-key against CURRENT beets defaults — defaults changed across versions (his track_length_grace 2/max 10 were old defaults, now 10/30; his weights ≈ OLD beets defaults + zeroed edition penalties) and I wrongly claimed parity before the user caught it.**
- **Log-based diagnosis of the running addon:** `ha_get_logs(source="supervisor", slug=<slug>)` returns the container log (newest window; `order=oldest` for chronological). Readable progress = albums processed alphabetically, per-album blocks interleaved (threaded importer); `musicbrainz: Requesting MusicBrainz release <uuid>` = plugin active; `lastgenre: <album> - <track>` count == item count = per-track lookups happening.

## lastgenre — source-verified (beetsplug/lastgenre/__init__.py) + preview without applying
- Plugin config defaults: `whitelist: true` (built-in genres.txt), `min_weight: 10`, `count: 1` (user: 4), `canonical: false`, `force: false`, `keep_existing: false`, `pretend: false`, `source: album`, `prefer_specific: false`, `title_case: true`, `aliases: true`, `cleanup_existing: false`, `fallback: None`.
- **`force: no` (default) → existing genres are KEPT.** The log line `Resolved (keep any, no-force): [genres]` is logged at **DEBUG** — invisible at `-v`, which is why genre results never showed in the addon log while the lookup lines (`lastgenre: X - Y`, INFO) did. "Looked up but not visible" ≠ not working.
- `_fetch_and_log_genre` structure: `log.info(str(obj))` (the visible lookup line) → resolve → `log.debug("Resolved ({}): {}", label, genres)` (hidden at -v) → `ui.show_model_changes(obj, fields=["genres"])` (prints `genres: [old] → [new]` diff in CLI runs).
- **Preview without writing: `beet lastgenre -p` (--pretend = "show actions but do nothing" — verified in source: fetches + logs + shows diffs, skips `try_sync`).** Combine with `-A` (items; default is albums) and add `-vv` to see the Resolved lines: `beet -c <config> -vv lastgenre -p -A added:today`. Shows BOTH sides per track: existing (Tidal) → Last.fm result, zero writes.
- **Store BOTH genres:** `force: yes` + `keep_existing: yes` combines existing + Last.fm genres into the list (Navidrome handles multi-genre) — the middle ground between "keep Tidal" (force: no) and "Last.fm only" (force: yes).
- **⚠️ Combine is NOT a pure union — the whitelist filters KEPT existing genres too (source-verified `_filter_valid`):** `keep_existing` merges existing + Last.fm, but the merged list runs through `_resolve_genres` → `_filter_valid` (`if not self.whitelist or g.lower() in self.whitelist`), which drops ANY genre not in the whitelist — INCLUDING existing ones — then truncates to `count` (`valid_tags[:count]`). Live proof: existing `['pop','dance','electronic']` + last.fm tags → `Resolved: ['Pop','Electronic','Electro House','House']` with `- Dance` in the diff. `dance` is NOT in beets' bundled genres.txt (1,568 lines — verified `grep -ix 'dance'`). **Raising `count` does NOT rescue non-whitelisted genres** — truncation happens AFTER the whitelist filter. The user hit this as "I lost tags!": when proposing combine, warn explicitly that existing genres are still whitelist-filtered and count-capped.
- **`whitelist: false` = the "don't rely on the whitelist" switch (pure union):** existing AND new tags all pass unfiltered (only `count` caps). Keeps Dance, but lets last.fm junk through (`french`, `catchy`, `female vocalist`, `seen live`…). Middle path: `whitelist: true` + custom whitelist entries (proposed `genre_whitelist_extra` option). `genre_mode` maps: keep → `force: no`; overwrite → `force: yes`; combine → `force: yes` + `keep_existing: yes`. `count: 4` is HARDCODED in run.sh's heredoc — raising it needs a new option (`genre_count` — SHIPPED PR #26, **default 12**; `genre_whitelist` default `false` = the pure-union switch is ON by default, `genre_whitelist_extra` list-of-strings appends to the whitelist when enabled).
- **Undo reality (user asked "can I undo what beets did?"):** no beets undo command exists. Import writes are metadata-only (genres rewritten, titlecase, MB IDs added, art added — no moves/deletes, `copy/move: no`). Recovery = re-download from Tidal via Octo-Fiesta, or accept; the old genres appear in `-vv` logs (`existing genres taken into account: [...]`) but parsing them back is fragile (import.log rotates at 10 MB). `force: no`/keep mode = future imports preserve existing genres VERBATIM ("keep any, no-force" returns them unchanged — the whitelist never touches existing genres, source line 416).
- Tidal vs Last.fm genres: Tidal = 1 broad catalog tag written by Octo-Fiesta (e.g. `Pop`, sometimes wrong); Last.fm = up to `count` community tags, whitelisted (only real genres) + canonicalized (`synth pop` → `Synthpop`), per-track when `source: track`.
- **Verification commands for the running addon (Terminal & SSH, NOT the agent container — no docker/supervisor exec access from Hermes):** `docker exec addon_<slug>_beets beet -c /data/beets/config.yaml ls -f '$albumartist - $album - $title → $genres' added:today` (what's in the files), `ls 'genre::^$'` (missing genres), `ls -a has_cover_art:false`, `stats`, `grep -E 'Tagging|Matched|replaced' /data/beets/import.log` (import record).

## PR #28 — fetchart `sources:` must be a LIST + log-filter completion (Aug 2026)
- **Beets 2.x `fetchart.sources` REQUIRES a YAML list.** The config-port heredoc wrote a scalar (`sources: coverart itunes filesystem`) → `sanitize_pairs` receives it as ONE unknown pair → `UnknownPairError: setting coverart itunes filesystem is not recognized` → `** error loading plugin fetchart` → the ENTIRE plugin fails to load. **Symptom is SILENT for imports:** the error appears once per `beet` invocation (startup + every subcommand run), imports continue, but NO cover art is fetched anywhere. The generated-config validation recipe (yaml.safe_load) does NOT catch this — the YAML is valid, only beets' schema semantics reject it. Fix: list form (`coverart`, `itunes`, `filesystem=*`).
- **awk blacklist completed (PR #28):** added `!/^titlecase: .*does not exist/` (benign per-candidate noise) and `!/^ftintitle: \//` (per-track `ftintitle: /media/music/…` path lines; keeps real ftintitle change lines, drops the "Not changing" + path spam).
- **\"The lines didn't disappear\" — filter fixes only take effect after merge + REINSTALL (user: \"re-analyse before we merge\"):** the running image predates the fix, so the noise/error legitimately persists in the CURRENT logs. Before claiming a log fix works: pull the LIVE window via `ha_get_logs(source=\"supervisor\", slug=<slug>, order=\"oldest\")` and confirm the lines are gone. **A clean window is NOT proof either:** ID-match albums (chroma \"ID match.\") produce NO titlecase noise — those lines only appear during candidate evaluation (`Evaluating N candidates`) on search-fallback albums.
