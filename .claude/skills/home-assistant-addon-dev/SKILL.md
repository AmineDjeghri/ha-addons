# Home Assistant Add-on Development

This skill governs the creation and maintenance of Home Assistant (HA) add-ons, emphasizing a modular monolith architecture and a seamless GitHub $\rightarrow$ HA update pipeline.

## Trigger Conditions
- Creating a new HA add-on.
- Adding a new service/API to an existing HA add-on.
- Troubleshooting deployment or configuration issues in HA.
- Removing a capability or mapped mount from an existing add-on (evidence procedure: `references/addon-capability-hygiene.md`).
- Deciding where an app's config lives, or a path that works on the host but not inside the container (naming, `app_configs` rename, probe-both discovery, what you cannot read from a container: `references/haos-app-config-paths.md`).

- Auditing which installed add-ons are the user's own / deletable / unversioned: `references/addon-inventory-audit.md`.

## Core Architecture Principles
- **Modular Monolith:** Prefer a single "Hub" API (e.g., FastAPI) with multiple `APIRouter` modules over a swarm of small add-ons to minimize DevOps overhead.
- **Disposable Containers:** Treat the container as immutable. Store all runtime data and state in `/data`. **Choosing the mount (he asks this repeatedly — answer with the taxonomy, never a guess):** `/data` is the app's private persistent volume (always present, included in snapshots, DELETED on uninstall) and is the right home for state — DB, cache, credentials. `addon_config` is the only mount that surfaces as `/config` *inside* the container (backed by `/addon_configs/<repo>_<slug>`) and exists for files a human provides or inspects: user-supplied config, an app DB or log someone must browse — user-writable, so never the home of a live SQLite DB. `homeassistant_config` is HA's own config tree (`secrets.yaml`, `.storage`): read-only when an app must consume it, never a place to write app state. `share`/`media` are cross-app data. Repo precedent: `hermes-webui` mounts `all_addon_configs:rw` to SHARE the agent home between two containers, `octo-fiesta` carries `config:rw`+`media:rw` from its upstream image, `beets` mounts only `media:rw` with state in `/data/beets`, and `aiostreams`/`mediaflow-proxy-light`/`personal-app` declare no `map:` at all (least privilege — every mount is another exposure path). `map:` is applied at container CREATION: switching mounts needs a reinstall, not a restart. **Before keeping OR dropping a `map:`, verify the ARTEFACT it exists for — never the README's word for it.** An add-on tracking a foreign upstream image inherits mounts from that upstream's compose file and they are often vestigial. Worked case (octo-fiesta `config:rw`): its only justification was `Subsonic__PlaylistsDirectory`, which upstream applies as a directory NAME under `Library:DownloadPath` — the `.m3u` files land in `/media/music/playlists/`, already covered by `media:rw` — and `run.sh` wires no Tidal vars, so upstream's `/config/tidal-tokens.json` example does not apply. Evidence chain = the artefact listed on disk (`ls /media/music/playlists`, visible because the agent container mounts `/media`) + the app's own path semantics from upstream docs + **the app's OWN startup log**, which prints its state paths at boot (octo-fiesta: `Token store: /app/tidal-tokens.json` — its own directory, never HA's config). The agent container CANNOT read HA's `/config`, so before dropping a mount ask the user to confirm nothing landed in the config root (File editor, 10 seconds).
- **Configuration:** Use `config.yaml` options and access them via `bashio` in the `run.sh` script.
- **Deployment:** Follow the native HA update path: GitHub Release $\\rightarrow$ HA Supervisor $\\rightarrow$ User clicks "Update".
- **Share data, not environments:** In multi-container add-on setups, share persistent *data* (HERMES_HOME, workspaces) between containers — never Python venvs. Each container keeps its own disposable env (PyPI installs); shared venvs couple independent update lifecycles and break when the same dir is mounted at different container paths.
- **Persistence (the `HOME` trick):** Docker containers are ephemeral by default. NEVER rely on `/root` — set `ENV HOME=/data/<addon>` (or `/config`) in the Dockerfile so pip user-site packages, `gh` auth, and tool configs land on a persistent HA volume. Give each add-on its own HOME subdir to avoid `.lock` contention and shared-config corruption between containers.

## Where Batch Jobs Run — host vs addon vs n8n vs Hermes
Decision framework from the beets/Navidrome analysis (Aug 2026) — applies to any script the user wants off a bare host crontab:
- **Files decide the host.** A job that touches the music/media library (`/media/music`) belongs in a container with `map: media:rw` — local-disk I/O. From the host, HAOS `/media` is only reachable over a network share → slow scans, tag writes over the wire.
- **Never custom-code an upstream-tracked image addon** (octo-fiesta pattern: `build.json` pins `ghcr.io/<owner>/<repo>:<tag>` + nightly `upstream-bump.yml`). Foreign, fast-moving base; every bump recreates the container and kills long-running jobs; a base-image change silently breaks your pip layers. Worst host for a batch CLI.
- **Batch CLI ≠ service.** A long-running proxy (octo-fiesta) or web app (personal-app) restarts on every update — a multi-minute `beet import` must not share their container. Batch jobs get their own stable container or a host systemd timer with `OnFailure=` notification (upgrade from bare crontab: journald logging, boot-safe ordering, failure alerts).
- **n8n = orchestration/notification layer, not a CLI runner.** Execute Command runs in the n8n container (no beets/python deps, no media mount). Wrong tool for heavy CLIs.
- **Hermes cron = observability layer here.** ~~The agent addon mounts only `/config` + `/addon_configs` (no `/media`), so it can't run file-touching jobs~~ — **CORRECTED Aug 2026 (verified via /proc/mounts + live listing): the agent addon (WolframRavenwolf v1.3.1, Debian 12) now mounts `/media`, `/share` AND `/data` ALL rw** — it sees the real music library (`/media/music/…FLACs` listed from inside the agent). The agent CAN run file-touching jobs on the library: `uv` at `/usr/local/bin/uv`, `ffmpeg` already at `/usr/bin/ffmpeg`. **The chat-driven YouTube pipeline is BUILT (Aug 2026): project `/config/workspace/youtube_ai_download/` (skill `yt-dlp-music-downloads`, symlinked into `~/.hermes/skills/media/`) — a PEP 723 script run via `uv run --no-project yt_dl.py` (NO global install; uv builds a cached Python 3.14 + yt-dlp + mutagen env on first run), with 100% LLM-decided metadata through overrides.json — no parsing heuristics (user's explicit design: "rely 100% on the LLM"). Flow: agent downloads → staging (outside the watch root) → atomic folder move into `/media/music/YouTube/<playlist>/` → the beets addon's inotify watch auto-imports+tags (live bootlegs → asis fallback). Navidrome consumption tip: albums are named `Live at <venue> (year)`, so ONE smart playlist (Album contains 'Live') collects every download automatically (beets triggers startScan after imports); non-music clips go to `YouTube/Other/` with album `Other` so they stay out of that playlist. Old "observability layer only" claim is stale — re-verify mounts before asserting what the agent can't do.
- **Event-driven > polling.** Octo-Fiesta downloads continuously; the ideal trigger is inotify on `/media/music` with debounce + flock, with a daily incremental timer as fallback — not a 5-minute cron.
- **Evidence discipline (the user audits claims — "how did you know?"):** HAOS `/media` == host `~/haos_media` is *deduced* from `map: media:rw` + `library_download_path: /media/music` (octo-fiesta config.yaml) + the host crontab path in their docs. The *transport* (Samba vs virtiofs/9p vs bind mount) is inference until `mount | grep haos_media` / `virsh dumpxml haos` confirms. When asserting architecture, cite the file + tool and separate verified vs inferred.

## From-Scratch Python Addon Pattern (personal-app model)
For addons with no upstream Docker image (pure Python apps), personal-app is the reference (verified Aug 2026):
- `build.json`: `{"build_from": {"aarch64": "ghcr.io/home-assistant/aarch64-base:latest", "amd64": "ghcr.io/home-assistant/amd64-base:latest", "armv7": "ghcr.io/home-assistant/armv7-base:latest"}}` (Alpine HA base images, `:latest`).
- `Dockerfile`: `apk add --no-cache curl` → install uv (`curl -LsSf https://astral.sh/uv/install.sh | env UV_INSTALL_DIR="/usr/local/bin" sh`) → `COPY pyproject.toml uv.lock` → `uv sync --all-packages --frozen` (exact locked versions; uv auto-downloads its own Python) → `COPY run.sh` + `ENTRYPOINT ["/run.sh"]`.
- bashio install that works on apt OR apk bases (octo-fiesta Dockerfile): install `curl ca-certificates bash jq`, then curl the `hassio-addons/bashio` v0.16.2 tarball, extract `lib/` → `/usr/lib/bashio`, symlink `/usr/bin/bashio`. ⚠️ **Only needed on FOREIGN upstream bases.** The HA base images themselves (`ghcr.io/home-assistant/{arch}-base` Alpine AND `{arch}-base-debian`) ALREADY ship bashio + curl + jq + ca-certificates — running the install on them fails the build (`ln: failed to create symbolic link '/usr/bin/bashio': File exists`, verified 2026-09 in mediaflow-proxy-light CI). On HA bases, skip the whole install RUN. Note `base-debian:latest` currently = Debian 13 trixie. Related bashio fact (v0.16.2): `bashio::config` resolves options ONLY via the Supervisor API (`GET /addons/self/options/config`, envelope `{"data": {...}, "result": "ok"}`) — it IGNORES `/data/options.json`; bashio honors `SUPERVISOR_API` env override, so CI smoke tests of run.sh need a fake supervisor server (or the local bashio cache at `/tmp/.bashio` goes stale between runs — clear it in sims).
- `config.yaml` defaults: `init: false`, minimal `options`/`schema`. `map:` is NOT added by default — personal-app mounts nothing; add `media:rw` explicitly when the addon needs the music/media library.
- **PyPI-package upstream tracking (beets case):** no Docker image to pin. `config.yaml version:` = the upstream package version, Dockerfile pins `pkg==X.Y.Z`, and the `upstream-bump.yml` job fetches latest from `https://pypi.org/pypi/<pkg>/json` → `info.version`, sed-replaces both files, regenerates CHANGELOG.md from the GitHub release body. HA shows an update whenever upstream releases. App config: beets 2.13+ auto-backs up library.db before schema migrations (`create_backup_before_migrations`, built-in, DEFAULT yes — no config needed; one `<db>-before-<table>-<migration>.bak` per migration ever, never rotated, few MB each) so auto-bumped upgrades don't corrupt state. Full beets proposal in `references/beets-addon-design.md`.
- **Addon-ONLY fixes when `config.yaml version:` mirrors upstream (Aug 2026, beets PR #20 — user's FINAL choice):** keep `version:` = upstream package version and deliver addon-code fixes via **manual reinstall** — do NOT bump an addon patch suffix; the user explicitly rejected the `<upstream>.<addonpatch>` scheme ("I will manual reinstall yes, it's better I think for now"). If a suffix IS ever proposed again: HA compares `2.13.1.1` as newer than `2.13.1` and offers an Update, and the nightly bump job needs companion changes to avoid a spurious downgrade commit — gate on the upstream-only part (`BASE=$(printf '%s' "$CURRENT" | cut -d. -f1-3)`), and sed-replace ANY suffix (`sed -i -E "s|^version: \"[0-9]+\.[0-9]+\.[0-9]+[^\"]*\"|version: \"${NEW}\"|"`). ⚠️ **Uninstall deletes the addon's `/data`** (library.db, import progress, logs): preserve around the reinstall with `docker cp app_<slug>:/data/<dir> /tmp/backup` BEFORE uninstall, reinstall, then `docker cp /tmp/backup app_<slug>:/data/<dir>` while the addon is STOPPED, then start — the startup import resumes incrementally.
- **HA builder wheel index breaks pip/uv resolution — use uv CLI flags, NOT env vars (corrected Aug 2026 after PR #18+#19):** the Supervisor builder injects `https://wheels.home-assistant.io/musllinux-index/` as the ONLY pip index — it's baked into the HA base image as `/etc/pip.conf`, not just an env var. It mirrors OLD wheel versions, so a fresh dependency needing a newer release fails: beets 2.13.1 requires `mediafile>=0.17.0`, the index only has `mediafile<=0.13.0` → uv `No solution found when resolving dependencies`. uv's first-index-wins (dependency-confusion guard) means adding PyPI as an EXTRA index does NOT fix packages already present (at old versions) on the first index. **Env overrides FAIL**: `env -u PIP_INDEX_URL -u UV_INDEX_URL UV_DEFAULT_INDEX=https://pypi.org/simple` still resolves against the HA index — uv honors the base image's pip.conf over UV_DEFAULT_INDEX (build failed identically on the user's HA, PR #18). The fix that actually builds is uv **CLI flags** (highest precedence, beat pip.conf) plus `--index-strategy unsafe-best-match` so any leftover index can't downgrade a dep; keep a temporary `--virtual` build-base for C deps lacking musllinux wheels:
  ```dockerfile
  RUN apk add --no-cache --virtual .beets-build build-base \
      && uv tool install --python 3.14 \
             --default-index https://pypi.org/simple \
             --index-strategy unsafe-best-match \
             "pkg[extras]==X.Y.Z" \
      && apk del .beets-build \
      && ln -s /root/.local/bin/tool /usr/local/bin/tool
  ```
  build-base is heavy (~415 MiB installed) — deleted in the same RUN so only build time pays; slim to `gcc musl-dev` if wanted. The `InvalidDefaultArgInFrom` warning (empty BUILD_FROM default) in build logs is benign — standard for HA addon Dockerfiles.
- **HA backups and addon `/data`:** full backups include a per-addon "Building backup for add-on <slug>" stage covering `/data` + `/addon_configs`; `/media` inclusion is a user choice — THIS user excludes /media (music re-downloadable), so a restore returns the DB without files (index points at missing tracks; harmless, heals on re-download). Growing addon logs in `/data` bloat archives — truncate/rotate.

## Pitfalls & Lessons
- **ha-addons conventions are canonical in the repo's root `AGENTS.md`** (added Sep 2026): read it first when working in that repo — layout, branch/commit/squash rules, git-identity email rule, CI-scope reality (no checks outside `personal-app/**`), versioning-by-type (never suffix-bump PyPI-tracked addons), persistence + `run.sh` 100644, detect-secrets pragmas. This skill holds the deeper addon-building knowledge; the repo file is the always-current contract — when a convention changes, edit the repo file first, not this skill.
- **Secret-scan false positives: fix structurally, never pragma-first (Sep 2026, GitGuardian on a public repo):** GitGuardian flags password-SHAPED literals on PRs — a deliberate throwaway default (`AUTOINSTALL_PASSWORD="${...:-pos-dev}"`) tripped "Generic Password". Restructure so no secret-shaped literal exists (default the password to another resolved variable: `${AUTOINSTALL_PASSWORD:-$AUTOINSTALL_USER}`) and amend + force-push the single-commit PR so the flagged content leaves branch history — the re-scan then passes and the incident clears. A pragma/`# ggignore` plus a NEW commit does NOT clear an incident on an old SHA (dashboard dismissal required). Corollary: never bake the owner's name into default credentials in a public/forkable repo — scrub to a generic value, and scrub BOTH the code default and the doc line documenting it (a doc-only scrub is dishonest while the code default persists).
- **Declare API/mount permissions explicitly in `config.yaml`** — they default to OFF and silently gate every API call at runtime:
  - `homeassistant_api: true` → addon can call the HA Core REST proxy at `http://supervisor/core/api/*` with `Bearer $SUPERVISOR_TOKEN`. Without it: **401**.
  - `hassio_api: true` + `hassio_role: default` → addon can call supervisor API (`/addons`, `/store`, `/info`). Without it: **403** (only `/info` works).
  - `map: - homeassistant_config:ro|rw` → mounts HA's `/config` (automations.yaml, .storage) into the container. Other mount types: `share`, `media`, `backup`, `ssl`, `all_addon_configs` (exposes every addon's config dir).
  - Runtime symptom → missing declaration: `curl http://supervisor/core/api/states` → 401 means `homeassistant_api` missing; `/addons` → 403 means `hassio_api` missing. Bump `version:` after editing so the supervisor offers the update.
- **Probe the auth matrix empirically before exposing any add-on to the internet (verified Sep 2026, mediaflow proxy):** a README's blanket "all endpoints require the password" is not evidence — run the binary/container and record which paths answer without credentials. When a repo has several addons but ONE semantic-release pipeline (e.g. only `addons/personal-app/` is versioned), unrelated work in another addon (like `hermes-webui`) can spuriously release the wrong package:

- **`workflow_dispatch` (manual "Run workflow") bypasses `paths:` filters** — a manual run triggers the whole pipeline even when the filtered path didn't change.

```bash
LAST=$(git describe --tags --abbrev=0 2>/dev/null || git rev-list --max-parents=0 HEAD)
if git diff --name-only "${LAST}..HEAD" | grep -q '^addons/personal-app/'; then
  echo "changed=true"  >> "$GITHUB_OUTPUT"
else
  echo "changed=false" >> "$GITHUB_OUTPUT"
fi
```
…then run the semantic-release step only `if: steps.changed.outputs.changed == 'true'`. (Use an `if/else`, not `&&/||`, to stay safe under `set -e`.) Also fix the run-summary so the no-op case reads accurately (report "no releasable changes", not a misleading success/failure).
